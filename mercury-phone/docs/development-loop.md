# Mercury Phone 功能开发准则

这份准则是每次新需求的固定工作流。

## 1. 共同完善想法

收到一个功能想法后，先明确：

- 用户要解决的问题和使用场景
- 主流程、异常流程和退出方式
- 数据来源、保存位置和跨应用边界
- 空、加载、成功、错误、禁用、编辑、删除状态
- 隐私、离线、性能和无障碍要求
- 明确不做什么

先形成一张功能卡并确认意图，再进入实现。

## 2. 细分任务

每个功能拆成：

1. 产品规则
2. 数据契约与 Store
3. Bridge 或系统服务
4. UI 页面、组件和状态矩阵
5. 视觉参考与示意图
6. 功能接线
7. 单元测试、真实运行和视觉验收

没有确认数据边界和状态矩阵前，不先堆 UI 或接口。

## 3. UI 参考与设计

用户可以提供即时设计或其他免费资源网站的链接、截图和素材。参考前检查许可证，免费不等于可以商用或重新分发。

设计阶段固定执行：

- 先读取 Mercury 当前视觉基线、配色、字体、圆角、安全区和动效
- 选择成熟软件作为交互参考，只借鉴任务结构和成熟模式
- 使用 taste skill 输出设计读取、设计变量、页面结构和状态示意图
- 先确认示意图，再实现正式 UI
- 不把参考代码、文案、图片、图标、专有命名带入正式项目

taste skill 负责视觉质量和反模板化检查；Mercury 的原生脚本架构、数据契约、可访问性和真实产品交互优先级更高。

## 4. 实现闭环

按以下顺序落地：

`数据模型 → Store → Bridge → UI → API 或 AI → 持久化 → 测试 → 视觉验收`

页面能打开不代表功能完成。必须能从真实入口触发、保存、恢复，并在失败时给出明确反馈。

## 5. 发布门禁

发布前必须：

- 删除整个 `reference-sources/`
- 扫描正式代码、文档、测试、资源和构建产物中的外部专有痕迹
- 检查第三方代码、字体、图标、图片和 UI 资源的许可证
- 重建 `dist/`，不把开发期参考文件带入产物
- 运行 `npm run release:check`、必要的视觉截图和人工复核
