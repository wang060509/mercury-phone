## 三、必须记住的 API 现状

`app/core/chat-contracts.js` 已经有 `memoryCandidates` 契约，支持以下记忆类型：

- `fact`
- `preference`
- `commitment`
- `shared_event`
- `open_thread`

本轮已经完成最小闭环：

1. provider 可以通过 `〔记录〕...〔/记录〕` 标记、扩展字段或约定的 `tool_calls` 返回候选。
2. `server/upstream-client.js` 会过滤首版不支持的类型，补齐用户回合和助手回合来源，并过滤非法候选。
3. `mercury-chat-app.js` 会把候选写入待确认记录 Store。
4. 联系人主页可以确认或暂不记录，只有确认后的内容才会进入“重要时刻”。
5. 记录标记会在服务端被移除，不会泄漏到聊天气泡。
6. 待确认记录可以先编辑内容，再确认写入；确认后的版本才会进入时间线和下一次上下文。

下一步正确链路：

```text
模型输出候选
  → 服务端结构化校验
  → 前端待确认列表
  → 用户确认或拒绝
  → 保存为关系记录
  → 联系人主页展示
  → 经确认的记录回注下一次对话上下文
```

候选记忆不能未经确认直接写入。关系状态也不能因为一次对话自动推进。

## 四、明天优先级

### P0：记忆候选最小闭环（已完成）

已完成一条可验证路径：

1. provider 返回一个合法的结构化候选。
2. 服务端保留合法候选，过滤非法候选并产生 warning。
3. Chat 收到候选后进入“待确认”状态。
4. 用户可以确认或暂不记录。
5. 确认后写入独立的关系记录 Store。
6. 联系人主页读取确认记录，展示在“重要时刻”。
7. Store、代理层和 UI 已有测试覆盖。

建议第一版只支持 `shared_event` 和 `open_thread`，因为它们最适合联系人主页的共同回忆与未完成话题，不要一开始处理所有类型。

### P1：API 失败和空状态

- provider 不返回候选时，聊天必须正常完成。
- 候选格式错误时，不能阻塞助手回复。
- 用户拒绝后不应再次自动出现同一候选。
- Store 写入失败时显示明确的本地保存错误，不静默丢失。

以上四项也已完成第一版：重复内容幂等、拒绝状态不会再次出现、记录写入异常会与聊天回复隔离并显示保存提示。

已确认的关系记录会在下一次请求中回注运行时上下文；只回注 confirmed 记录，不回注 pending 或 dismissed 记录。
