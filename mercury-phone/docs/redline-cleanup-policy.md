# 参考作品 · 落地清洗规范（红线执行机制）

> 日期：2026-08-02
> 目的：用户明确担忧——开发难免参考优秀作品，万一有**只言片语/专有名词**留在源码里，被懂行的人（甚至 AI 代理人战争）看出来就是抄袭铁证、身败名裂。为守住「只借结构/框架、绝不复现名字/剧情/角色/专有名词」红线，本文件把清洗变成**机械执行**，而非靠自觉。
> 这套机制**长期保留**（它本身就是守门人），与 `reference-sources/`（阅后即焚的敏感源码区）分开存放。

---

## 0. 一句话原理

**「参考」和「抄」的分界，不在"有没有看过参考"，而在"落地产物里有没有独一无二的、可指认原型的痕迹"。** 借结构/框架 = 合法；留下能被人指着说"这是从 XX 抄的"的专有名词/剧情/句式 = 违规。本规范是查这个"痕迹"的机器，不让它靠人眼靠记忆。

---

## 1. 两条硬规则

1. **所有有参考而落地的产物（预设/世界书/角色卡/任何生成文本），入库前必须过一遍 §3 的专有名词词表查重。** 词表里出现的任何词都不能出现在落地产物里。
2. **`reference-sources/` 文件夹在项目公开前必须整份删除**（它进 `.gitignore`，绝不进任何 commit，但删除仍要做，防止 git 历史或备份残留）。

谁负责记得？不是靠人记忆——`docs/dev-progress.md` §0 顶部已加"公开前必做清单"，每个跨会话断点都读它。

---

## 2. 文件布局

```
reference-sources/          ← 阅后即焚的「参考源码」隔离区（.gitignore，公开前删）
  README.md                 ← 说明这份里放了什么来源、何时删
  (参考源码/主题/预设原文)     ← 来源作品的原始文件，只放这不进 git
docs/
  redline-cleanup-policy.md ← 本文件：清洗机制（长期保留）
  (落地产物会写到 app/ 和正常的 docs/)
```

> 关键分两区：**敏感源码**进 `reference-sources/`（会删）；**清洗机制/提炼出的方法论笔记**留在 `docs/`（不被污染、沉淀下来反复用）。提炼笔记也是脱敏产物——只能讲结构框架，不能带专有名词。

---

## 3. 专有名词词表（敏感数据，随 reference-sources 一起删）

每次处理一批参考作品，先抽一份**该作品的专有名词清单**，放 `reference-sources/banlist.md`：

```markdown
# 禁止出现词表（随 reference-sources 删除，勿外泄）

来源：<作品/项目名>
- 角色名：A、B、C…
- 地名/世界观专名：X、Y…
- 特有称呼/口癖：……
- 剧情独家设定：……
- 项目/插件特有名：……
```

**执行**：落地预设/世界书/角色卡时，生成的文本逐项过这表。命中任何一个 → 该产物算"带原型痕迹"，需重写该处，直到零命中。

**注意**：词表本身也是敏感数据，**不得进 git、不得公开**；随 reference-sources 一并删除。它只作为"落地时对照的本地清单"存在。

---

## 4. 落地查重的执行方式（作为哨兵）

- **工具产出时自检**：每写一个落地产物（尤其生成器文本、世界书条目、角色卡 persona），把 `reference-sources/banlist.md` 读进来，对产物做字面扫描。零命中才入库。
- **结构框架可借，专有痕迹不可留**：照参考的"分几点/怎么组织"，但每个词、每句都换成我们自己的。参考教会我们"该怎么分块、防油腻要写在哪一层"，不告诉我们"这句要说成原样"。
- **查不到名字不算过**：真正要过的是"专有名词 + 独家剧情 + 独有句式"。结构框架（如"三层分离：人设管事实/纪律管活人感"）是通用方法，不是某作品的独有财产，不算违规。

---

## 5. 公开前必做清单（写进 dev-progress §0）

发布/第一次 push 前，逐一确认：
1. `reference-sources/` 已整份删除（最迟这一步）。
2. 源码/文档里 grep 一遍所有已知专有名词，零命中。
3. 确认 `.gitignore` 里 `reference-sources/` 在；如果历史里误提交过，重写历史（若用户授权）。
4. 提炼出的方法论文档（docs/ redline、reference-phone-architecture 等）均已脱敏——只讲结构，无任何专有名词。
