# Mercury Phone 整体实施提纲

日期：2026-08-09  
性质：长期架构与开发顺序提纲  
原则：视觉沿用当前 taste 设计方向；功能按 Mercury 自己的产品想法决定；外部小手机教材只提供结构启发。

## 0. 产品定位

Mercury Phone 是一部围绕 AI 陪伴设计的虚拟手机。手机壳、桌面、系统叠层、应用切换和通知不是装饰，而是产品体验本身。

两条主柱保持平等：

- Home：让用户相信这是一部可以生活在其中的手机。
- Chat：让用户相信自己正在和一个持续存在的人联系。

当前视觉基线已经形成：390 × 844 移动设备比例、低饱和浅色、通透玻璃、雨滴与水面材质、Manrope 字体、克制的系统动效。后续功能不能为了“更像某个参考”而改变这套基线。

## 1. 现有工程基线

当前正式运行面由以下几部分组成：

1. 系统壳：启动、锁屏、PIN、状态栏、灵动岛、控制中心、通知中心、Home Bar、应用切换器、桌面与小组件注册表。
2. 正式应用：Settings、Mercury Chat、Archive。
3. 本地服务边界：静态服务、本地代理、聊天请求、连接测试。
4. 数据与逻辑：ConversationV2、ChatExperience、Archive 资源模型、角色档案、世界条目、提示模块、UserPreset、Runtime Core、AITransport。
5. 演示隔离层：Moments 等 `.local-demo` 内容，只用于展示，不进入正式数据和生产构建。

当前最重要的事实：

- 系统壳和视觉方向已经足够作为基础，不做一次性重构。
- 角色档案的编译输入、预设装配和聊天请求已经有部分接线。
- 世界条目、提示模块、时间线、关系状态、长期记忆还没有形成完整的运行时闭环。
- 部分 UI 仍是暂定版或占位版，不能把“看得到”当作“功能已完成”。

## 2. 目标架构

外部教材最值得借用的是“每个领域自己负责、系统通过明确边界连接、复杂功能按需装载”的思想。Mercury 保留自己的注册式应用壳，不复制参考项目的全局命名空间和文件组织。

### 2.1 系统壳层

系统壳只负责设备体验和系统级状态：

- `SystemShell`：设备框、安全区、壁纸、状态栏、Home Bar。
- `SystemStateMachine`：boot、locked、unlocking、home、app、overlay、switcher 等合法状态。
- `SystemServices`：命名空间存储、通知请求、主题请求、灵动岛活动、应用桥接。
- `AppEngine`：应用注册、生命周期、独立 DOM 根、错误隔离。
- `WidgetService`：小组件注册、位置申请、未来编辑器。
- `InputRouter`：手势、点击、键盘预览和系统边缘动作。

约束：应用和小组件不能直接修改系统壳 DOM；所有跨层请求必须经过服务或桥接。

### 2.2 应用层

每个正式应用都遵循同一份应用合同：

```text
manifest
  id / name / icon / version / capabilities
factory
  create(context)
lifecycle
  render / onMount / onPause / onResume / onUnmount
domain entry
  routes / commands / empty-loading-error states
```

首批正式应用继续保留：

- Mercury Chat：会话、联系人、角色主页、个人页、预设、聊天呈现。
- Archive：角色档案、世界、提示模块、来源资产、导入审查、实例连接。
- Settings：AI 连接、主题、锁屏、通知、桌面组件、数据与隐私。

未来需要的“深入小程序”不直接堆进 Chat，而是作为独立应用包接入。每增加一个应用，都必须先有产品目标、数据合同、入口、状态矩阵和退出方式。

### 2.3 领域数据层

不建立一个包揽一切的全局 store。每个领域拥有自己的存储和 schema，通过显式 bridge 交换最小数据。

建议的领域边界：

| 领域 | 负责内容 | 不负责内容 |
|---|---|---|
| ChatStore | 联系人快照、会话设置、ConversationV2 | 不直接拥有 Archive 原档 |
| ArchiveStore | 来源资产、角色档案、世界、提示模块、实例 | 不直接渲染 Chat |
| RelationshipStore | 关系阶段、信任、主动性、重要事件索引 | 不改变角色本质 |
| MemoryStore | 记忆候选、长期摘要、关键事件、保留策略 | 不删除原始对话 |
| UserStore | 用户身份、用户人设、个人偏好 | 不改写角色档案 |
| PresetStore | 玩法预设、模块选择、偏好输入 | 不承载呈现主题 |
| ThemeStore | 主题变量、壁纸、图标、字体偏好 | 不改变运行时语义 |
| MediaStore | 头像、背景、相册、音频等大资源 | 不把二进制塞进 localStorage |

小数据先用命名空间 localStorage，图片和音频达到规模后迁移 IndexedDB。所有 store 都要有版本、normalize、坏数据保留、统一提交入口和迁移测试。

### 2.4 Runtime Compiler

`buildRuntimeInput()` 是四件套和聊天之间的唯一装配入口。它负责把领域数据翻译成一次请求所需的运行时输入：

```text
Core
  → 安全与产品规则
  → 当前会话模式
  → 用户预设
  → 角色档案
  → 生效世界条目与提示模块
  → 时间线与关系状态
  → 长期记忆与近期上下文
  → 生成前纪律尾部
  → compiledSystemText + provenance + warnings
```

权威边界固定：

- Core 负责角色演绎的最高层规则。
- 用户预设可以调玩法、关系起点、主动性、偏好和呈现节奏。
- 角色档案负责身份、历史、价值观、动机、能力和边界。
- 世界与模块负责背景和可生效规则。
- 美化只改变呈现，不改变角色选择、知识和动机。
- 生成前纪律必须靠近生成位置，且不能被用户预设覆盖。

### 2.5 AI 请求与消息呈现层

AITransport 只负责请求和取消，不负责决定角色是谁。Chat App 负责：

- 请求前生成运行时输入。
- queued、processing、delivering、complete、failed、cancelled 状态。
- 结构化 AssistantTurn 与多段气泡。
- 心声/旁白的结构性剥离，不能混入可见正文。
- 失败、重试、重新生成、取消和超时反馈。
- 记忆候选的接收与后续写入。

格式纪律和逐条发送节奏分开设计：前者是编译层合同，后者是呈现层行为。

### 2.6 可插拔小程序层

未来的日记、相册、时间线、纪念日、关系空间、语音、群聊或其他功能，不按参考产品的名称和列表直接复制，而按以下模板评估：

1. 这个功能对用户的生活感或陪伴感解决什么问题。
2. 它属于哪个领域 store。
3. 它是否需要新的应用壳，还是 Chat/Archive 内的子功能。
4. 它有哪些数据状态和空态。
5. 它如何通过 bridge 与 Chat、通知、关系或记忆交互。
6. 它在离线、本地存储、失败和删除时如何工作。
7. 它是否会引入新的媒体存储或服务依赖。

只有完成这份判断，才进入 UI 和代码实现。

## 3. 四件核心能力的实施路径

### 3.1 角色档案

目标：角色档案可创建、导入、审查、编辑、导出，并能以快照方式进入聊天。

顺序：

1. 角色档案垂直切片：Archive 创建或导入 → ready 状态 → 导出/桥接 → Chat 联系人 → 编译 → 真实发送。
2. 联系人实例覆盖：同一档案可以创建多个聊天实例，实例可以独立覆盖显示名、头像、关系阶段和部分呈现偏好。
3. 版本与回滚：档案修改可追踪，已导入的联系人默认不被静默覆盖。

### 3.2 世界与模块

顺序：

1. 手动启用的世界条目进入编译。
2. 按 scope、visibility、enabled、priority 过滤。
3. 增加关键词或上下文触发。
4. 增加条目关联、角色绑定和会话绑定。

### 3.3 用户侧能力

分成两个完全不同的领域：

- User Persona：用户是谁，进入用户侧身份资料。
- User Preset：用户想怎么玩，进入玩法控制层。

预设 UI 可以继续采用“一卡一模块”的自适应结构，但要用正式视觉规范重做暂定样式，并保留导入、导出、冲突提示、即时预览和当前会话绑定状态。

### 3.4 美化与主题

顺序：

1. `tokens.css` 从单一根变量改为 `[data-theme]` 作用域。
2. 主题切换通过现有 `theme:requested` 接缝完成。
3. 主题包只包含变量覆盖、壁纸、图标和字体偏好。
4. 主题导入导出使用 Mercury 自己的边界格式。
5. 主题与角色、记忆、世界、预设完全解耦。

## 4. 系统体验补齐顺序

1. 先收口已有入口：桌面图标、小组件、Me、Settings、聊天加号面板不能静默失败。
2. 完成聊天核心状态：发送、等待、失败、取消、重试、重新生成、心声分离。
3. 完成 Archive → Chat 的档案垂直闭环。
4. 完成世界与模块的编译接线。
5. 完成记忆候选、长期摘要、关键事件和关系状态。
6. 完成预设正式 UI 与会话绑定。
7. 完成主题系统与个人资料编辑。
8. 以用户明确提出的功能为顺序增加深入小程序，每次只做一个完整闭环。
9. 最后再扩展群聊、语音、关系空间、日历、纪念日等长期能力。

## 5. 每一项工作的固定流程

每个功能都按同一条节奏推进，不一次性重构：

1. 讨论：明确用户任务、范围和不做什么。
2. 设计：写数据模型、状态矩阵、入口和退出路径。
3. 架构：确定所属领域、store、bridge、编译输入或系统服务。
4. UI：沿用当前 taste 设计系统，先做空态、加载、成功、失败、禁用、编辑和删除状态。
5. 实现：只改当前垂直切片，不顺手重写其他模块。
6. 验证：单元测试、真实运行态、截图、键盘/触摸基础检查、构建和生产审计。
7. 记录：更新进度、未决问题和下一步，不让进度文档落后于代码。

## 6. 参考教材的使用边界

允许吸收的内容：

- 领域 store 独立。
- 应用功能内聚并按需加载。
- 小程序拥有自己的状态和数据边界。
- 运行时分层、靠近生成位置的纪律尾部。
- 短期上下文与长期摘要并存，原始历史不被摘要替代。
- 特殊消息使用结构化合同，不把所有内容当普通文本。

禁止带入的内容：

- 外部作品的名称、角色、地点、世界设定、专属标签和专属字段名。
- 外部作品的原句、独特提示词、独特剧情、角色关系和可识别桥段。
- 外部项目的全局命名空间、文件名、应用名、路由名、测试样例和 UI 文案。
- 仅因为参考里有某个功能，就把它加入 Mercury 的产品路线。

执行方式：外部格式只能在导入边界被识别，进入 Mercury 后立即翻译成自研 schema；内部 storage key、变量名、路由名、测试 fixture、UI 文案和生成文本全部使用 Mercury 自己的命名。

## 7. 发布前清洗门禁

`reference-sources/` 继续作为本地隔离区，开发期间不进入提交。公开或交付前必须完成：

1. 删除整个 `reference-sources/`，包含原始源码、原始素材、清单和词表。
2. 清理源码、测试、文档、注释、fixture、文件名、图片元数据和生产产物中的外部专名与可识别痕迹。
3. 将当前仍带有外部格式称呼的内部代码改成中性命名。
4. 扫描 `app/`、`docs/`、`tests/`、`dist/`、`package` 和部署清单，命中即阻断发布。
5. 确认 `.gitignore` 仍隔离参考目录，并检查首次提交前没有被误加入版本历史。
6. 做一次人工复核：即使词面零命中，也不能保留独特句式、角色关系、世界设定或剧情痕迹。

这一步是发布门禁，不是开发功能；在门禁前不公开、不交付、不把参考目录复制到其他工作区。

## 8. 当前建议的第一项

先做“边界清洗与运行时基线”这一项：

- 盘点并替换当前代码、测试和文档中的外部格式命名。
- 保留导入兼容能力，但把它收束在边界翻译函数内。
- 更新进度文档，让 2026-08-09 的 Settings 和预设实际状态进入权威记录。
- 为发布前扫描增加可执行检查，但暂不删除本地参考目录。

完成并验收这一项后，再开始下一项“Archive 角色档案 → Runtime Compiler → Chat 请求”的完整垂直闭环。

## 9. 当前不做的事

- 不一次性重构整个工程。
- 不为了参考教材新增一整套外部产品功能。
- 不把外部 schema 变成 Mercury 内部 schema。
- 不在正式产品中保留参考作品名称、原文或易识别变体。
- 不把演示页面当作正式功能完成。
- 不在 UI 尚未定义状态矩阵前先堆接口或服务。
