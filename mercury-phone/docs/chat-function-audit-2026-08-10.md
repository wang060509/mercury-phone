# 聊天功能审计（2026-08-10）

## 结论

当前不是“完整聊天功能”，而是已经跑通了一个可验证的**单联系人文本聊天闭环**：输入文字 → 兼容 API → 返回多气泡文本 → 本地保存 → 结构化记忆候选进入待确认区。

这条闭环已经具备继续开发的基础，但聊天产品仍处在 P0/P1 功能补齐阶段。全局视觉统一应该继续后置，不能替代聊天主链路建设。

## 已完成的聊天闭环

1. 现有联系人进入会话。
2. 文字输入、发送、发送状态和失败状态入库。
3. 本地代理向兼容 API 发起请求并解析回复。
4. 回复可以被拆成多个短信气泡，心声内容与正文分开。
5. 回复中的关系记录候选进入待确认区。
6. 候选内容可以编辑、确认、拒绝，并回显到联系人关系时间线。
7. 点击助手消息可以重新生成；点击用户消息可以删除。
8. 联系人档案、世界绑定、确认关系记录可以进入运行时上下文。

相关实现入口：[mercury-chat-app.js](../app/apps/mercury-chat-app.js)、[chat-contracts.js](../app/core/chat-contracts.js)、[ai-transport.js](../app/core/ai-transport.js)、[upstream-client.js](../server/upstream-client.js)。

## P0：必须先补，否则不能称为完整聊天

### 1. 设置项与真实生成没有完全接上

当前对话设置页提供时间流动、角色主动性、关系节奏、戏剧强度、上下文范围、记忆处理等开关，但请求生成时主要使用 `conversation.settings` 和 `unspokenAside`；这些体验设置没有形成完整的运行时输入。

具体风险：用户以为切换了玩法，模型实际可能没有收到对应规则；`contextScope` 没有改变历史窗口，`memoryHandling` 也没有真正决定候选如何处理。

### 2. “流式回复”开关与传输层不一致

设置页显示流式回复已开启，但上游请求固定使用 `stream: false`，前端也没有增量解析、停止生成或中途失败恢复。

需要先定义产品行为：要么真正实现流式，要么暂时关闭这个开关并明确显示“非流式”。不能让用户看到与实际能力相反的状态。

### 3. 失败后没有可用的重试闭环

发送失败会留下“发送失败”状态，但用户消息的操作只有删除；`lastError` 没有形成对话内错误提示、重试按钮和重新发送策略。

最低闭环应是：失败原因可见 → 重试原消息 → 防止重复生成 → 成功后替换失败状态；超时、认证错误、限流和上游不可用要有不同提示。

### 4. 新建会话没有实际流程

聊天列表的“新建对话”目前只是切换扩展面板，没有联系人选择、导入后开始会话、空会话创建和重复会话处理。没有这个流程，后续多联系人能力无法自然扩展。

### 5. 会话状态字段还没有形成列表行为

数据里已经预留 `pinned`、`hidden`、`muted`、`unread`，但聊天列表没有据此排序、过滤或显示；静音也没有接入通知，未读也没有在收到回复时更新。

## P1：社交聊天基线缺口

这些是普通社交软件中用户会默认期待的能力：

- 多联系人会话搜索、筛选和最近会话排序。
- 群聊或多人角色会话的数据模型与成员显示。
- 引用、回复、转发、复制、编辑、撤回、反应/表情回应。
- 图片、贴纸、语音消息等富消息类型；当前消息契约只有文字和助手文本 parts。
- 历史消息搜索、长会话分段加载、草稿保存。
- 会话导出、导入、清空和删除前确认。
- 失败、发送中、已送达、已读、生成中、停止生成的统一状态机。
- 角色主动消息、后台消息和通知中心的联动。
- 聊天背景、气泡、字体的真实预览和当前会话应用范围。

当前扩展面板里的“图片、表情包、转账、红包”点击后只是写入 `data-state="coming"`，不是功能入口。截图证据见 [03-composer-actions.png](../artifacts/chat-audit-2026-08-10/03-composer-actions.png)。

## P1：AI 角色扮演能力缺口

### 已有基础

- 角色资料能够参与运行时编译。
- 世界和关系记录已有接线入口。
- 预设、正文分泡、心声清洗、记忆候选都有契约。

### 还没有形成成熟闭环

- 世界资料、角色资料、历史对话和生成纪律目前主要合并成一个 system 文本；缺少“历史之后、紧贴生成前”的不可覆盖纪律层。
- 只有关系事件/未完成话题候选，没有长期对话总结、重要记忆、记忆去重和摘要注入策略。
- 心声现在是自由文本旁白，不是可管理的结构化“状态/行为/独白”记录。
- 主动性、时间流动、关系节奏等设置还没有调度器或明确的生成规则。
- 重新生成是覆盖当前回复尾部的简单分支，没有版本、分支、保留旧回复或回滚策略。
- 没有上下文检查器，用户看不到下一次请求到底携带了哪些角色资料、世界资料、记忆和历史。

## 对照参考架构后的判断

参考的小手机项目把聊天、多联系人、群聊、富消息、记忆、世界资料、主动消息和深入应用拆成多个领域，并且把本地数据按领域隔离。它的价值在于展示完整产品边界，不代表 Mercury 要一次复制全部功能。

对 Mercury 最重要的借鉴顺序应该是：

1. 先把聊天领域的会话、消息、生成、错误、记忆和上下文检查做成稳定闭环。
2. 再补新建会话、多联系人、未读/静音/隐藏/置顶和历史搜索。
3. 再补富消息与角色主动消息。
4. 最后扩展群聊、情侣空间、相册、钱包和其他深层应用。

## 下一阶段建议：聊天闭环 v1.1

### 第一批，先做 P0

1. 统一“对话设置 → runtime input → API request”的映射。
2. 解决流式开关与真实传输的矛盾：实现流式，或先关闭假开关。
3. 增加失败提示、重试、取消生成和重复请求保护。
4. 实现新建会话页：联系人选择、空会话、导入联系人后开始聊天。
5. 实现未读、静音、隐藏、置顶的列表行为。

### 第二批，再做 P1

1. 历史搜索、草稿和长会话分段加载。
2. 完善消息操作：复制、引用、编辑/删除策略、重新生成保留分支。
3. 设计富消息契约，先落地图片和贴纸，再考虑语音、转账、红包。
4. 长期记忆总结与上下文检查器。
5. 角色主动消息与通知联动。

只有第一批稳定后，才进入全局视觉统一；届时视觉调整会有真实状态可展示，也更容易判断哪些组件应当共用。
