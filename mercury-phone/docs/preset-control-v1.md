## 0. 为什么做成「模块装配」而不是「一段 instructions」

成熟预设产品的共性（已阅后即焚，只留框架）：**预设不是一条长文本，而是一个「可装配的模块清单 + 顺序 + 开关」**。要点：

- **必开骨架 + 选开内容**：少数模块是「别关」的硬骨架，绝大多数是「按需开」的可选能力。
- **组内互斥争用（多选一）**：同一个能力位放多个候选模块，用户选一个激活，避免指令互相打架；而不是全部叠加。
- **能力位 = 被替换的槽**：选中的模块写入某个玩法槽，替换默认，保证一致。
- **分隔线横幅做区块**：相近模块归一组，组有「开启/结束」标记。

`compileRuntime()` 现有的 `userPreset.instructions` 槽（`chat-contracts.js:180-227`）已经是「一条文本」形态。v1 的做法：**保持 `instructions` 作为编译产物入口，但由 `UserPreset` 契约的生成器把它组装出来**。契约只存「一个模块列表（含组归属、开关、生成文本）」，生成时按序拍平成 `instructions`。这样既满足两轴、又不破坏现有运行时接口，同时让预设天然支持任意条目、数量自适应。

## 1. 契约结构（独立于 DEFAULT_SETTINGS）

> ⚠️ 切记 `dev-targets.md §目标B` 的格式陷阱：这套必须**独立命名空间**，**不得并入 `DEFAULT_SETTINGS`**（那货是呈现层，管 replyLength/bubbleMode/maxBubbles/deliveryPacing/actionText/unspokenAside + context + memory。玩法层是另一档）。

### 1.1 顶层

> 核心原则（随用户输入定稿）：**预设不存一份"固定玩法字段"，只存一个"模块列表"**。设置页不是固定分段控件，而是**瀑布卡片式**——每一张卡 = 一个模块，随预设条数自动扩展。四条内置玩法（关系起点/戏剧强度/主动性/偏好）只是内置的**四组模块**，不是一份必须固定的 schema。上传预设带多少条目就渲染多少张卡。

```jsonc
{
  "id": "preset-<name-ascii>",        // 全局唯一，装配进 presetId 槽
  "name": "预设显示名",
  "version": 1,
  "modules": { ... },                 // §1.2 整个预设就是一个模块列表
  "custom": {}                        // §1.3 用户自写指令（可选，低权）
}
```

### 1.2 模块是唯一原语（`modules`）

预设的全部玩法偏好 = `modules`。每个模块是一片**可开关、带组归属、带生成文本**的玩法指令：

```jsonc
"modules": {
  "order": ["group.rel.respect-card", "group.int.balanced", "group.pro.initiative", "pref.focus", "skeleton.preserve-role"],
  "enabled": { "group.rel.respect-card": true, "group.int.balanced": true, ... }
}
```

- **组（group）**：互斥能力位。一组里只能激活一个候选（如关系起点组：respect-card / stranger / familiar / lovers 四选一）。组内多选 = 状态不合法。
- **组间（cross-group）**：可叠加，例如同时有"关系起点组 + 戏剧强度组 + 主动性组 + 偏好项"。
- **骨架模块**：`skeleton.*` 是必开组，默认 on 且 UI 标"别关"。
- **偏好项（pref.*）**：非互斥，可开多个或全关。

**四条内置玩法 = 四组内置模块**（不再有固定 `active` 字段）：
| 组（互斥） | 候选模块 id | 语义 |
|---|---|---|
| `group.rel` | rel.respect-card / rel.stranger / rel.familiar / rel.lovers | 关系起点 |
| `group.int` | int.balanced / int.slow / int.high | 戏剧强度 |
| `group.pro` | pro.standard / pro.initiative / pro.reactive | 主动性 |
| `group.pref`（非互斥） | pref.focus / pref.address / pref.hard-off | 话题/称呼/边界 |

> 上传的预设可以带**不在基础库里的组/模块**（含模块文本随文件带来，`§8`）。此时设置页**照常渲染一张新卡**，不因"库不认"而丢弃或不显示——这正是瀑布卡片的意义：按条数自适应。

### 1.3 自定义区（`custom`）
- `custom.instructions`：用户自写的一段指令，**生成时排在所有模块段之后**，权重最低，不得覆盖角色本质（两轴）。同样以一张可展开的卡展示。

## 3. 生成器：实际文本内容（这段是"我写的文字"，直接进编译）

> 用法：`UserPreset.instructions` = 按 `modules.order` 把所有**启用模块**的生成文本依次拼接（互斥组取选中的那个，选开项取开启的那些），段间空行；最后接自定义段。骨架段在前。上传预设里不在基础库的模块，直接按其随文件带来的文本依序拼入，不因库不认而跳过。每段都以角色立场写，不带"系统提示/你要"式的机械前缀；角色表达应保持自然。

### 3.0 骨架
```
这是"玩法层"设定，用来调"你想怎么对话"，不是改写角色本质。角色是谁、它的价值观、动机、边界、知识范围，仍以角色档案为准。下面的设定只在玩法/关系/偏好的维度生效。
```

### 3.1 relationshipStart
- **rel.respect-card**：
```
这段对话的关系起点，尊重角色卡上写好的设定。如果卡上定了关系（比如熟人/恋人/初识），就照它来，不要因时间长短自动升温。
```
- **rel.stranger**：
```
这段对话从"陌生人初见"开始。角色和你素不相识，彼此都还没建立信任、没有共同过往。角色不会一开始就熟络、付托或袒露太多。
```
- **rel.familiar**：
```
这段对话从"熟识"开始。角色和你有一定交情、能自然接话，但仍保有各自的分寸，不必无话不说。
```
- **rel.lovers**：
```
这段对话从"恋人"开始。角色与你的关系已在亲密状态，信任和亲近是被认可的。但亲密不代表失去自我——角色的性格、原则、在乎的东西依然成立。
```

### 3.2 intensity
- **int.balanced**：
```
戏剧强度平衡：有来有往，不刻意制造冲突，也不刻意回避波折。顺着角色和情境自然发展。
```
- **int.slow**：
```
戏剧强度舒缓：少一点猛烈的推进，多留白和日常感。让关系、冲突、情绪都慢一点、质感更绵长。
```
- **int.high**：
```
戏剧强度偏高：可以有更强的拉扯、悬念和情绪起伏。但在角色性格与身份允许的范围内用力，不为了戏剧性背叛角色。
```

### 3.3 proactivity
- **pro.standard**：
```
主动性常规：角色主要回应你，但遇到在意的话题、没解决的事或合适时机，也会自然地提起或追问。不刻意找话说。
```
- **pro.initiative**：
```
角色偏主动：会主动带起话题、推进关系、追问被回避的事、分享自己最近的生活。主动来自角色自己的动机和性格，不是每轮机械开场。
```
- **pro.reactive**：
```
角色偏回应：以你的发话为中心，主要接着你的话题走，不主动转移或挑起新话题。但这不等于干答或只接不动——在对方的话题内，角色仍会带一点自然的推进（追问一句、把话递回、留一个由你接住的口子），只是不做话题主导者。
```
> 对齐核心基线 [Core 24]：reactive 控制的是「谁主导话题」（不主动挑新话题），不削弱「回话要带一个推进点」——推进点在对方话题内也成立。CI 与 C24 维度不同，不冲突。

### 3.4 preferences（各段可单独开关）
- **pref.focus**：
```
这段对话的话题，优先朝{initialFocus}展开。角色谈到相关处自然靠拢，但不必每一步都硬拽回来。
```
- **pref.address**：
```
你希望被用{address}称呼。角色会按这个称呼与你交流。
```
- **pref.hard-off**：
```
这段对话尽量避开这些：{hardOff}。除非你主动提起，否则角色不往这些方向带。
```

> `{initialFocus}` / `{address}` / `{hardOff}` 是运行时占位，从 `preferences` 用户文本注入，未填则不生成对应段。

## 4. 两轴校验（生成器里落一道轻约束）

1. **优先级**：预设排在角色档案之前——生成的 `instructions` 仍走 `compileRuntime()` 现有顺序（`runtime-core-v1.md §0.2`：用户预设 > 角色档案这层相对关系不变）。**本阶段不改编译顺序**，只保证 UserPreset 喂进 `userPreset` 槽即可。
2. **权威边界**：预设不得改写「角色是谁」。骨架段（§3.0）已声明这条；生成器对 `custom.instructions` 不做内容解析（低权），边界靠骨架文本约束即可到"可用"成熟度。深度校验（预设 vs 档案冲突裁决）留阶段三。

## 5. 数据 / 存储

- **独立命名空间**：遵循 `dev-targets.md` 的 `mercury.app.<appId>.<key>` 模式，专用 `mercury.app.chats.userPresets` 存预设列表。
- **每对话绑定**：`ConversationSettings`（`chat-experience-contracts.js` 里的 settings）加一个 `userPresetId: null` 字段（可空=用全局默认），指向预设。
- **默认预设**：一个内置 `preset-default`（骨架 `skeleton.*` + 每类互斥组各选一个中性候选），未显式启用时兜底。可直接装配的完整数据见下方 §5.1。
- **结构合法性**：`UserPreset` 需过一道校验，确保 `modules.enabled` 里互斥槽没同时选两个、`order` 只含已启用项。

### 5.1 内置默认预设数据（可直接装配）

> 生成时：`preset.instructions` = 按各段生成文本依 `order` 拼接，段间空行，骨架在前。**活人感基线在核心**（core-v0.2），不在此重复——预设只带玩法，不带反 AI 味。此数据为 `preset-default` 的权威样本。

```jsonc
{
  "id": "preset-default",
  "name": "默认预设",
  "version": 1,
  "modules": {
    "order": [
      "skeleton.preserve-role",
      "skeleton.mode",
      "group.rel.respect-card",
      "group.int.balanced",
      "group.pro.standard"
    ],
    "enabled": {
      "skeleton.preserve-role": true,
      "skeleton.mode": true,
      "group.rel.respect-card": true,   // 互斥组 rel：选 1
      "group.int.balanced": true,        // 互斥组 int：选 1
      "group.pro.standard": true         // 互斥组 pro：选 1
    }
  },
  "custom": { "instructions": null }
}
```

- **生成文本**：逐段取 §3——
  - `skeleton.preserve-role` → §3.0 第 1 段
  - `skeleton.mode` → §3.0 第 2 段
  - `group.rel.respect-card` → §3.1a
  - `group.int.balanced` → §3.2a
  - `group.pro.standard` → §3.3a
- **组内互斥**：`group.rel` / `group.int` / `group.pro` 各只一个候选在 `enabled`，符合 §1.2 校验。若以后在这里改成别的关系起点/强度/主动性，只替换对应候选 id，组仍单选。
- **不启用**：`pref.*`（焦点/称呼/边界）默认全关，本默认预设不预填自由文本，需用户手动开。

## 6. UI 改动方向（交 codex 做，Claude 不动 UI）

> 蓝图约定（`four-piece-blueprint.md` §第二件）：预设编辑器 UI 属 UI 范畴，交 UI 负责人。以下是方向，不改动方向细节归 codex 定。

### 6.1 入口
- 在对话「设置」（铃铛/齿轮）里加一行「玩法预设」，点开进预设面板。

### 6.2 预设列表 / 启用
- 顶部：当前预设名 + 下拉/卡片列表切换（内置默认 + 已保存预设）。
- 每张预设一张卡：名称 + 一句话玩法概括 + 「启用/编辑/新建」。

### 6.3 编辑器（核心）：瀑布卡片式，按条目数自适应
> 随用户输入定稿：**不做固定四项的分段面板**，改成**瀑布卡片**——每一张卡对应一个模块，卡片列表随 `modules.order` 逐张堆叠，加几个模块就有几张卡。内置四组玩法只是默认初始卡片序列；上传预设带多少条就渲染多少张，命名和布局都不写死。

- **卡片 = 模块**：每张流水卡片显示一栏——模块标题（如"关系起点"）、模块 id/组归属、开关（选开可关，骨架标"必开"只读）、当前选项（若该模块在互斥组内）。
- **互斥组的单选呈现**：同组候选模块作为**一张组卡内的一组选项点**，点哪个高亮哪个；群组内永远只亮一个（状态校验在 §1.2 已定）。
- **组卡堆叠顺序** = `modules.order`，可拖拽排序；新增/来自上传的未知模块，自动在末尾追加一张新卡，不因库不认而消失。
- **自由文本模块**（如 pref.address 称呼 / pref.hard-off 边界）：卡内嵌一个文本框，填了才产生对应指令段。
- **自定义指令** 收成底部一张可展开的卡（§1.3 `custom`），权重最低、标注"不改角色本质"。
- **即时预览**：右侧/底部实时显示将生成的 `instructions` 瀑布（只读），让用户看到文字效果——这是确认「读取正确玩法化」的直接反馈。
- **存为预设 / 命名**：底部「保存为新预设」+「重命名」。

### 6.4 结构化与呈现分层（别混）
- 预设面板只管玩法层；呈现层（气泡长度/分泡/心声/动作描述）留在原有设置区，**不同入口，不合并**。

### 6.5 状态反馈
- 对话顶部或设置里显示当前生效预设名，用户能知道"现在玩这套玩法"。

## 7. 底层修正（基础层行为基线）

「还是僵硬/像讲课」的病根不完全在玩法预设，而在**全局基础层**——所有对话应有的「活人式」基线，不该由每个预设或每张卡各自堆。参考里成熟预设把「反答题腔/对话指南」放**默认核心包**（全局基线）而非交给角色。这部分和预设不同：预设调"你想怎么玩"，基础层修"角色怎么说才像活人"。

### 属基础层的（进 Runtime 全局基线，非预设）
| 基线 | 内容要点 |
|---|---|
| 反答题腔 | 不接力科普、不按"背景→历史→原理→结论"铺开、不一次性交代设定，有话就说、说短、说透，允许说完就停 |
| 平衡三动作 | 一句话最好兼具「回应 + 自己的情绪/态度 + 一个推进点」；连续猛答、连续猛问都是僵硬 |
| 走体验不走知识 | 讲"我当时的感受/那天发生了什么"，不搬运定义、年月、条目式知识点 |
| 知识边界 | 只说自己亲历/听到/能合理推断的；对方没问的全景知识不主动讲 |
| 反总结收尾 | 不用"总之/所以你要…"做总结，允许留白、丢一句随手的观察 |

> 定位：这组是**基础层基线**（=`reference-preset-architecture.md` 里"全局通用规则放默认核心包"那一课），所有角色、所有预设之上默认继承。预设不改这条基线，只在其上叠加玩法。

> **2026-08-02 定案（路A）**：已把这组**写入 `runtime-core.js` 全局核心**（新增 `[Core 23] 反答题腔` / `[Core 24] 平衡三动作` / `[Core 25] 走体验不走知识` / `[Core 26] 反总结收尾`，版本 core-v0.2，规则共 30 条）。**并入核心＝全局必开不可关**：不设开关、不做成 skeleton 模块、不进预设 UI、不在预设层面覆盖。`知识边界` 一项原有规则已含，未重复新增。预设只在其上叠加玩法，触及这条基线即视为越权。

## 8. 用户上传预设（便携文件 + 导入）

用户不止想要内置预设——要能**上传别人写的/自己导出的预设**。复用 `archive-app.js` 现成的 JSON 导入链路（`openFilePicker` → `<input type=file>.accept=.json` → 读文本 → `prepareImport` 审核预览 → `confirmImport` 入库），不另造一套。

### 便携文件格式（导出即上传）
预设可整体导出为一个独立 `.json`：
```jsonc
{
```

### 导入校验（安全红线）
> 对齐 Archive「原始内容以纯文本保存，不会自动执行，也不会自动进入聊天」的精神（`archive-app.js:293-294`）。预设是文本，不上传代码、不执行脚本。

1. **识别**：`kind === "mercury.user-preset"` 且 `PresetFormat` 可解析，否则提示"不是可识别的预设文件"。
2. **结构校验**：过 §1 的合法性校验（互斥槽不多选、`order` 只含已启用项、模块 id 在库里能找到或带入模块文本）。**未知模块 id > 丢弃该模块**，不静默吞坏文件。
3. **审核预览**：入 `import-review` 一档，展示「预设名 / 玩法档位摘要 / 含多少模块 / 是否有自定义指令」，用户确认才启用/保存。
4. **命名冲突**：导入了同 id 预设，建议「另存为副本」（id 追加 `-copy-N`），不覆盖用户已有的。

### UI 方向（交 codex）
- 预设列表/编辑器里加「导入 JSON」与「导出」按钮，走现成的 file-picker。
- 导入后进审核页（复用 Archive `import-review` 皮肤），通过后进已保存预设列表。
- 同名/同 id 冲突弹「覆盖 / 另存副本」二选一。
