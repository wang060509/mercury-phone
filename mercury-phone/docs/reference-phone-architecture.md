# 小手机应用 · 整体架构对标（参考开源项目）

> 日期：2026-08-02
> 性质：**架构对标笔记**（持续参考，非阅后即焚）。复盘一个浏览器端"小手机"聊天应用的整体结构，供 Mercury 对标开发、突破瓶颈。
> 红线：**只借结构/框架，不复现任何专有名词**。源码已脱敏——所有原始变量名、角色名、应用名、特有标签一律抽象化，只保留"它是怎么分层的、每层解决什么问题"。

---

## 0. 为什么是它

Mercury 卡在瓶颈期：功能要得多、不知道从哪下手、担心"东做一点西做一点自己脑补"。这个参考项目的价值在于它是一个**已经跑通的前端单页"小手机"**——和我们"手机级沉浸"同一类形态。它的整体架构（非人设细节）正是我们缺的"整套体系"参照。

**它对我们最重要的一件事**：证明了"小手机"可以**完全无后端**——数据全存浏览器本地，纯静态前端。这验证了 Mercury 现在选型的上限，也给出了能走多远的答案。

---

## 1. 顶层形态与运行方式

| 维度 | 参考项目 | 对 Mercury 的参照 |
|---|---|---|
| 形态 | 浏览器端静态单页"小手机" | 与"手机级沉浸"一致，无需改形 |
| 后端 | **无后端**，纯前端 | 验证 Mercury 无后端可行 |
| 数据存储 | `localStorage` / IndexedDB / OPFS | Mercury 现状方向一致，需补 IndexedDB 大块（图片/相册/音频） |
| 构建 | 无构建步骤，原生 JS + 顺序 script | 与 Mercury 现状完全一致 |
| 运行 | 需静态服务器（非 file://，因 http(s) 依赖） | **注意**：Mercury 现在想 file:// 直跑，这里给出差异 |
| 授权 | 需自填 API 地址+密钥，仓库不含密钥 | 与 Mercury 现状一致（无内置密钥） |
| 安装 | PWA，可"添加到主屏" | Mercury 可选扩展点 |

**含 PWA**：`manifest.json` + `service worker`。安装到桌面是沉浸感的一部分——Mercury 阶段二可对标。

## 2. 功能模块划分（对比缺口）

参考项目宏观上拆成三大块：**桌面/系统壳、聊天、深入模拟小程序**。

| 大类 | 参考子模块 | Mercury 现状 | 差距 |
|---|---|---|---|
| 桌面/壳 | 杂志风多页桌面、自定义 4×7 图标栅格、长按拖拽、widget 库、美化中心（壁纸/图标/字体/锁屏 PIN）、PWA | 有 SystemShell 壳、状态机、毛玻璃 tokens | 缺自定义桌面、widget、美化中心、锁屏 PIN |
| 聊天 | 多联系人、群聊、红包、朋友圈、相册、钱包、语音/通话/录像、翻译、心声、情诗、记忆抽取、感知规则 | 有聊天、联系人、心声(`unspokenAside`)、档案导入 | 缺群聊、红包、钱包、通话、心声的"数值化/独立档"、记忆抽取、感知 |
| 深入改装 | 模拟微信/SMS/小红书/抖音/B站/小说/健康/待办/游戏/云/浏览器/外卖/购物 | 无 | 这是"沉浸感"的大头，缺最多 |
| 交友 | 匹配、情侣空间（打卡/时间轴/悄悄话/相册）、日记/纪念日 | 无 | 缺 |

**结论：聊天是 baseline，深入模拟 app + 美化中心是"小手机沉浸"的差异点，也是我们产能缺口的真正大头。**

## 3. 数据层：无后端设计的存储分工

参考项目没有**一个全局 store**，而是**每个功能域自己一个 store**（聊天一个、联系人一个、情侣一个、每个 deep app 一个），通过 store 命名空间隔离。这对 Mercury 是重要参照：

- **领域隔离**：聊天 store 不该知道情侣 store 的内存。各 store 自持，跨域只通过显式 bridge。
- **关系 store 独立**：联系人-联系人之间的关系单独一个 store（`relationship`），不和联系人本身混——因为"关系"是多对多、会被聊天/情侣/世界书多处读。
- **易变数据用 localStorage，大块二进制用 IndexedDB/OPFS**：图片、音频、相册不能塞进 localStorage。

> 直接的架构启示：我们有一堆 `experienceStore`、`archiveStore`、`conversationStore`。参考项目告诉我们——**关系、长期记忆、世界书、用户多套自我面具，都值得拆成独立 store，而不是塞进某个 app 的 settings。**

---

## 4. 应用注册 / 系统壳

参考项目是**单 index.html + 大量顺序 script**，不是真正的应用容器注册制。但它的"模拟小程序开关壳"（每一个 deep app 是独立可开启的壳）和 Mercury 的 `MercuryAppEngine` 应用注册制**是同一个抽象的两个方向**：

- 参考项目：功能**内聚在个别 JS 文件**，靠项目级全局命名空间互调。
- Mercury：应用通过稳定 id 注册、生命周期 `onMount/onPause/onResume/onUnmount`、独立 DOM 根。

**结论：Mercury 应用注册制更规范，值得保留。参考项目的价值不在壳，在"模拟小程序怎么伪装真实 app 交互"。**

---

## 5. 懒加载

参考项目把我观察到的"非聊天模块"用 `lazy-boot.js` 懒加载，减少首屏。所有静态资源 URL 带 `?v=` 版本参数（缓存破坏）。

- Mercury 已有主 bundle 顺序加载。**缺口：非关键 app（深入模拟那些）可懒加载**，首屏只先加载桌面 + 聊天。
- `?v=` 版本号是低成本高回报的缓存策略，当前 Mercury 直接 file:// 可先不急着做，但上服务器后可补。

## 6. 聊天：人设与活人感的分层（本参照最值得搬的结构）

参考项目聊天提示词不是一条 system,而是"**1 个长 system + 若干独立 system 消息，插在历史之后、紧挨生成前**"。核心结构分三层：

### 6.1 三层分离

| 层 | 管什么 | 谁家 | 能否被覆盖 |
|---|---|---|---|
| **人设层** | "你是谁、什么关系"的事实 | 角色档案 | 可编辑 |
| **运转规则层** | 活人感纪律（防油腻/防复读/三段式纪律） | 全局 + 自定义预设可调 | **格式尾巴不可覆盖** |
| **感知层** | 时间/天气/时区/关系脉络 | 感知模块 | 自动 |

### 6.2 Recency 布局（最划算的一招）

提示词注入顺序是**越重要的越靠后、越近生成**：
```
主system(长提示: 全局→模式→用户→关系→感知→能力→格式) 
  → 历史对话 
  → 世界书后层 → 联系人档案(含人设) → 思维链 → 生成前最后确认 → 运转规则(置末)
```

**运转规则是最重要的纪律，放在所有 system/历史/别的块之后、紧贴生成。** 这样它离生成最近、上下文遗忘风险最低、不可被前面的人设/预设污染。

> 对 Mercury 的启示：我们 `compileRuntime()` 已有核心/安全/会话/用户预设/角色档案/世界书/临时 的优先级顺序。**缺的是"活人感纪律放在最末、且不被人设/预设覆盖"这一档**——这恰是我们 preset-control-v1 §7 想做但还没落成"置末不可覆盖"的地方。

### 6.3 防油腻的写法（不是点名 AI 毛病）

参考项目**没有一个字叫"别像客服/别说教/别油腻"的专门列表**（搜遍全仓库没有这些词）。它的做法反而是最有价值的：

```
"你是真实存在的人，有自己的生活和想法…你并非在扮演，你必须消化好人设与世界书，作出符合当下情境的对话；
不要油腻、不要凶很、禁止评判/威胁/控制的表达方式，要以温柔为底色，不要极端的去表达自己想要的东西或控制用户"
```

三连结构：
1. **正面定位**："你是真实存在的人，你并非在扮演"（对抗 AI 的扮演感）
2. **正向底色**："以温柔为底色"（给方向，不是给禁令）
3. **定向否定**："不要油腻、不要凶很、禁止评判/威胁/控制"（只点名极小的高危负面，不罗列一长串)

再加一条**跳跃性定义**（防僵硬的关键）：
```
"现在是线上聊天，须具备真人聊天的跳跃性、活跃性与不连续性：可碎片化、一句话拆成多条发、
中途转话题、隔几条再续上、语气忽然变轻或变冲；不必每轮都完整接话或逻辑闭环"
```

**防复读是硬纪律**（置末尾巴，不可覆盖）：
```
"发送前必须回顾上下文中你方近期已发原文：禁止频繁重复相同话题、相同描写/意象、相同动作套路、
相同句式或同质化撒娇/抱怨；主动找话题时勿反复提天气，勿复制上一轮结构与节奏"
```

> **这直接回答了我们一直纠结的"预设要不要加类型识别"——它没做。** 它不做"识别角色是温文尔雅型然后套模板"，因为它知道那会越权、会油腻。它把纪律做成"对所有人设生效、置末、不可覆盖"，人设只管"你是谁的事实"，活人感是独立纪律层。这正是我们 preset-control-v1 三番五次想守住的那个边界——而且它有现成的、验证过有效的一句话写法。

### 6.4 分泡：按换行切、不按句号，建议 1-5 条

- **每条换行一条气泡，不切句子**。
- **建议 1–5 条**，但属 soft：多也不硬截断，由模型按情绪决定。
- 富消息前缀系统：`表情包-`/`分享`/`语音-`/`图片-`/`引用-`/`转账-` 等——模型用前缀发"特殊气泡"，前端渲染成符号/卡片。
- 前缀串台是硬规则，禁止混用。

> 对 Mercury：我们 `maxBubbles: 4` + 按气泡切。参考项目的"按换行切 + 建议条数 + 富消息前缀"方向一致，但它没有句子级二次切分。**真正的"逐条发送节奏"在别处（房间模块），不是分泡文件**——说明分泡是格式纪律，发送节奏是另一个关注点，我们别混。

### 6.5 心声：不止独白，带数值仪表，独立成档

参考项目的"心声"比我们现在的 `unspokenAside` 高一档：

- **每轮必出**，结构 `thinking → 正文 → voice`，voice 严格最后。
- **自带 4 行默认字段**：
  ```
  好感度: <0-100>   欲望值: <0-100>   行为动作: <客观行为>   角色心声: <第一人称独白>
  ```
- 好感/欲望做成**环形仪表盘**，随轮滚动显示"内心快照"；每条心声绑定 msgId，进"心声档案"，头像高亮提示"这轮有心声"。
- 用户只看到 thinking 与 voice 之间的内容当气泡正文。
- 自定义心声可覆盖默认，用 JSON。

> **这正是我们要不要给 `unspokenAside` 升级的参照。** 我们现在只是"允许模型加一句旁白文本"。它把旁白做成**结构化数值 + 行为 + 独白**，让"活人感"变成用户**看得到的反馈**（好感涨了、在纠结什么）。酒馆级陪伴感靠这个才有。

### 6.6 记忆：短期窗 + 长期总结，零抹除

- **短期**：可调消息窗口（默认 40 条），每轮从尾部取最近注入。
- **长期**：回合结束触发异步总结，分类注入系统块：
  ```
  【长期记忆·对话总结】【长期记忆·角色重要记忆】【朋友圈·近期互动记忆】【线下场景总结】
  ```
- **关键：总结不抹原始历史**（"已沉淀的只作长期记忆块，不从窗口剔除原文，以免少注、断档"）——避免上下文缺口。

> 对 Mercury：我们 `memoryHandling: automatic` + `DEFAULT_SETTINGS.memory`。参考项目验证了"长期记忆 = 摘要块，注入时分类 + 不清原文"。这是我们记忆件该做的方向，且已写进 [[reference-preset-architecture]]。

## 7. 世界书：keyword 触发 + scope 范围 + 三层注入

- 条目字段：`id / enabled / scope / boundRoleIds / keywords / content / entryOrder`。
- **无关键词 = 必注入**；全局 reach = 强制。
- **scope 层**：local（绑联系人）、non-local（全员）、线上/线下/全局。
- **注入位置分三层**：front（主提示最前）/ middle（主提示中部）/ **back（独立 system 消息，放在历史之后、联系人档案之前）**。

> 对 Mercury：我们有 Archive `WorldProfile` + `worldBindings` 但没喂编译（dev-targets 目标C 未合）。参考项目的"front/middle/back 三层 + back 置历史后最近生成"就是我们要的接线方向。

---

## 8. 思维链 / 一致性

- **思维链 = 可编辑的"风格预设"**，不是固定 prompt。界面文案明确："此处写的是给模型的思维链风格指引，不是角色要发的正文；标签由角色每轮自行输出"。末尾格式硬性自动追加、不可编辑。
- **一致性落点不在"性格保持一致"，而在"防复读自查"**：强制"发送前回顾你方近期已发原文"。参考项目用这条防同质化，而不是试图用一条 prompt 维持"角色情绪永远稳定"。

> 对我们极关键：**"意识/一致性"是防复读自查，不是维持情绪稳定。** 这正好纠正我们可能的一个直觉——担心陆"情绪起伏是不是 OOC"，其实参考的做法是让角色自查别重复套路，情绪起伏是被允许的。

## 10. 对 Mercury 最值得先搬的 3 点（排序）

1. **纪律层置末、不可覆盖**——把"防油腻/防复读/三段式"放`compileRuntime()`最末、且用户预设法改不掉。这是治"陆油腻/僵硬"的根，且不越权。
2. **"正面定真人性 + 定向否定"的防油腻写法**——不罗列"别像客服"，三连：定位真人 + 给柔和底色 + 只点名几个高危负面。直接抄这句式到我们的 core。
3. **心声升级为"数值+行为+独白"独立档**——把抽象"活人感"变成可见反馈，是陪伴感升级的直接抓手。
